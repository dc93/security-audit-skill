# Server-Side Web Framework Hunting

#### When to use this file

Reach for this file when the target is a server-side web application built on a dynamic language and a framework of its own — PHP forums, CMSes, and community suites; Ruby/Rails, Python/Django-Flask, and Node MVC monoliths; anything with a custom ORM or query builder, a template engine it compiles or evaluates, and a plugin / theme / extension system. These stacks share a specific, high-hit-rate bug surface that `ATTACK-CLASSES.md` treats only generically: the injection class there says "trace input to a dangerous sink", but in these frameworks the dangerous sinks are *specific and non-obvious* — the ORM's raw escape hatch, a call to `unserialize` on cached bytes, a template the admin UI compiles to code, an extension archive that ships executable hooks. The safe default API hides them, so the reader assumes they aren't there.

Use this alongside `ATTACK-CLASSES.md`, not instead of it. Access control, business logic, and the client-side classes still apply; this file covers the server-side-framework layer where "it uses the ORM / the framework escapes output / it's a mature codebase" is the exact assumption being attacked. PHP is the primary example language below because it dominates this class (and its `unserialize`/`phar` and type-juggling behaviors are uniquely sharp); the patterns transfer — the ORM-identifier, template-to-code, extension-as-code, and deserialization classes exist in Ruby, Python, and Node equivalents, with the sink names swapped.

Pick the relevant classes based on Phase 1; split per subsystem (app/module, ORM layer, template engine, extension loader, REST API) for large targets. A framework this size almost always has more than one input-handling generation coexisting — audit the old one too (see the differential mode in `DIFFERENTIAL-AUDIT.md` when two versions are in scope).

## Core discipline (include in every agent prompt for this domain)

```
- The ORM is not a shield. Parameterization protects VALUES, not identifiers. Column names, table names, ORDER BY / direction, and any raw fragment (raw(), whereRaw, ->query(), string-interpolated WHERE) are unprotected. Find every raw escape hatch and every place a request field names a column, sort, or direction — that is where the query builder stops helping.
- Any unserialize / YAML.load / pickle / Marshal / Node deserialize on attacker-influenceable bytes is code execution IF a gadget chain exists, and the chain lives in the whole dependency tree, not just app code. Do not dismiss it as "no obvious gadget" — build the chain (phpggc for PHP) before concluding it's safe. In PHP, phar:// turns innocuous file functions (file_exists, getimagesize, fopen, is_file, md5_file, unlink) into an unserialize sink whenever the path is attacker-controlled.
- Template source is code. A theme/template editor, an admin field, or any store whose contents the engine COMPILES or EVALUATES is a code-execution sink — usually post-auth. The finding is the chain that reaches it: an ACP XSS/CSRF, a lower-privilege write into the template/hook/datastore store, an import that carries template markup. Reaching the sink is the work; the sink itself is a given.
- Comparison and coercion are attacker surface. Loose == , magic-hash 0e collisions, strcmp/hash on an array (returns null ~ 0), loose in_array — any auth, token, or signature check built on them is bypassable. Grep the check, don't trust it.
- Trust the code path, not the framework's reputation. A mature framework closes the default door. The finding is the app's raw escape hatch, its "for old clients" compat branch, or the custom sink someone built next to the safe API — never "the framework could be misused".
```

## Object injection and unsafe deserialization (subagent_type: `general`)

The densest source of pre/low-auth RCE in this class. Find every `unserialize()` (and `yaml_parse`, `Marshal.load`, `pickle.loads`, Node `node-serialize`) and trace its input: request bodies, cookies (a "remember me" or "redirect" cookie is a classic), cache/datastore entries, session payloads, import files, database columns that store serialized blobs. A framework that persists serialized objects in a datastore or cache and later rehydrates them is one write-primitive away from object injection — chain a lower-privilege write-to-cache with the deserialization read. For PHP specifically, hunt the `phar://` trigger: any file-system function (including deep in image processing, archive handling, or a `\File`-style abstraction) called on a path that includes an attacker-supplied filename or URL scheme deserializes the Phar metadata. Confirm a gadget chain exists in the loaded classes (magic methods `__wakeup`/`__destruct`/`__toString`/`__call`) — this is exactly where a runnable harness earns its keep: build the payload with phpggc, feed it to the isolated sink, watch it fire.

## ORM, query-builder, and second-order injection (subagent_type: `general`)

"It uses the ORM" is the lazy conclusion the injection anti-pattern warns about. Read every deviation from the parameterized path:
- **Raw fragments** — `raw()`, `whereRaw`, `selectRaw`, `->query()`, `DB::statement`, `find_by_sql`, `.where("... #{x} ...")`, or any string built into SQL. Trace the interpolated span to user input.
- **Identifier injection** — column names, table names, `ORDER BY`, and sort direction cannot be bound as parameters, so frameworks pass them as strings. A `sortby` / `order` / `col` / `dir` / `filter[field]` request parameter that maps to a column or ORDER BY clause is injectable even through a "safe" builder unless it's checked against an allowlist. This is the single highest-yield pattern in forum/CMS software — audit every sortable list, filterable table, and export.
- **Second-order** — input stored safely, then read back into a raw fragment or identifier by different code. A field name safe on write becomes a column reference on read; a serialized filter stored in a saved-search or a widget config gets spliced into a query later.
- **Query-builder operator/array injection** — where the framework accepts an array or object for a WHERE clause and an attacker controls its *shape* (nested arrays turning `WHERE id = ?` into `WHERE id IN (...)` or injecting operators/subqueries). Mass-assigned query conditions are the modern form of SQLi.

## Template, extension, and dynamic-code execution (subagent_type: `general`)

Where server-side code execution actually lives in these frameworks — rarely a bare `eval`, usually a system that turns data into code:
- **Server-side template injection (SSTI) and template-to-code** — engines that compile templates to native code (Twig, Smarty, Blade, ERB, Jinja, and custom compilers) execute whatever the template source expresses. Find every place template *source* comes from data: a theme/template editor in the admin panel, a stored theme setting, an email-template field, a user-supplied format string rendered through the engine. Persisted template markup that the engine compiles is an RCE sink; expression tags (`{{ constant('...') }}`, `{php}`, `_self`, `{expression=...}`) are direct evaluation. These are usually post-auth (admin/designer) — the finding is the *chain* that reaches the store: CSRF/XSS in the admin UI, or a lower-priv path that writes the template/hook store.
- **Extension / plugin / theme / module install as a code sink** — installing an add-on almost always means shipping executable code (PHP files, generated hook classes that extend core, migration scripts). Trace the install/upload/marketplace-fetch path: what privilege gates it, is the archive integrity-checked, can a non-admin reach it, does a remote fetch (marketplace, update server, URL param) let an attacker substitute the package? Hook/monkey-patch systems that compile add-on code into core class extensions are RCE by design — the audit question is only *who can trigger the compile*.
- **Dynamic dispatch and callable injection** — `call_user_func($userInput)`, `new $class($args)`, variable functions `$fn()`, variable methods `$obj->$m()`, `array_map($userCallable, ...)`, PHP legacy `preg_replace` `/e`, `create_function`, dynamic `include`/`require` (LFI/RFI). Any request value that selects a function name, class name, method, or file path to execute is the sink.

## File handling and server-side request forgery (subagent_type: `general`)

- **Upload → executable path** — an upload written under a web-served directory with an attacker-influenced extension (`.php`, `.phtml`, `.php5`, double extension, null byte, case tricks, `.htaccess` upload) is RCE. Check the extension/MIME/magic-byte validation *and* where the file lands and whether that path is executed by the web server.
- **Path traversal / local file inclusion** — user input in a file path (download, template selector, language/locale loader, avatar path, log viewer). Traversal to read secrets, or LFI escalated to RCE via PHP wrappers (`php://filter` chains, `data://`, `expect://`), session-file or log poisoning.
- **SSRF via the server's HTTP client** — the app fetches an attacker-supplied URL: avatar/image import from URL, webhook/callback registration, oEmbed/link preview, RSS/feed import, converter/migration fetch, update checks. Trace the URL to the fetch call; check for internal-network/cloud-metadata reachability, redirect following, and URL-parser differentials (the validator and the fetcher disagreeing on host). A fetch that returns the body to the user is exfiltration; one that only makes the request is still SSRF into the internal network.

## Framework auth, session, and mass-assignment (subagent_type: `general`)

- **Mass assignment / over-posting** — `Model::create($request->all())`, `->fill($_POST)`, `update_attributes(params)` where the model has a protected/security-relevant column (`is_admin`, `group_id`, `member_id`, `primary_group`, `verified`, price/balance). An attacker adds the extra field to the request and writes a column the UI never exposes. Find every bulk-bind and list what columns it can reach.
- **Type-juggling / loose-comparison auth bypass** — PHP `==` on a token/password/hash, magic-hash `0e...` collisions, `strcmp`/`hash_equals` misuse, an array passed where a scalar is expected to force `null`/`0`, loose `in_array`. Check password checks, token/CSRF comparison, signature verification, and "is this the right code" recovery flows.
- **CSRF and state-changing GET** — the framework's CSRF token model: is it enforced on every state change (including admin actions and API), or only on some forms? State-changing GET requests, or a token that isn't bound to the session, feed directly into the template/extension code sinks above (CSRF → admin template edit → RCE is the canonical critical chain in this class).
- **REST/API IDOR and privilege split** — the API surface frequently enforces different (weaker) checks than the web UI for the same resource. Diff the front-end controller and the API controller for the same object; check per-object ownership on `/api/*` reads and writes, and whether an API key / OAuth scope named `read` also lists drafts, other members' data, or admin-only fields. The admin vs front-end module split is where a control present in one is forgotten in the other.

## Universal moves (apply across the above)

- **Find the raw escape hatch, then walk backward to input.** Start from the dangerous primitive — `unserialize`, `raw(`, the template compiler, `call_user_func`, the extension installer — and trace *outward* to whether untrusted input reaches it. Power × reachability finds bugs faster than reading controllers top-down.
- **Map the input-object lifecycle.** In these frameworks a single request object (`\Request::i()`, `params`, `request.args`) fans out everywhere. Trace one tainted field through validation → ORM → storage → template → export and find the layer that assumed a previous one sanitized it.
- **Read the two generations side by side.** A framework this large keeps a legacy path next to the current one (an old controller, a deprecated API version, a compat shim, a converter from the previous major). The forgotten guard hides in the old path — and if a second version is in scope, run the differential mode in `DIFFERENTIAL-AUDIT.md`.
- **Confirm dynamically where the language allows it.** These stacks are locally runnable: extract the suspect function into a `php -r` / `irb` / `python -c` harness, build the deserialization gadget (phpggc), or render the template in isolation. A reproduced `id` in command output beats a paragraph of reasoning about magic methods.

## Validation rules (apply before reporting ANY finding here)

1. **For ORM/injection findings, name the exact escape from the safe path.** Cite the `raw()` / interpolated fragment / unchecked identifier and the request field that reaches it. "The app uses an ORM so it might be safe/unsafe" is not a finding — a parameterized query is not vulnerable, and an allowlisted sort column is not either. Confirm the identifier or fragment is genuinely attacker-controlled and not allowlist-validated first.
2. **For deserialization, show the sink AND argue the chain.** Point at the `unserialize`/`phar://`-triggering call with attacker-influenced bytes, and either exhibit a gadget chain in the loaded classes or state precisely which dependency provides it. A bare `unserialize` on data with no reachable gadget and no write primitive is a lead ("requires a gadget in the deployed class set"), not a confirmed RCE — but do the phpggc check before downgrading it.
3. **For template/extension code-exec, prove the reach, not just the sink.** The compile/eval/install sink being powerful is a given; the finding is *who can reach it and how*. State the privilege required and the concrete chain (CSRF/XSS/lower-priv write) that gets an attacker there. "Admins can edit templates" with no path for a non-admin to trigger it, in a design where admins are fully trusted, is designed behavior — not a finding (see Anti-Pattern 4 in SKILL.md).
4. **Verify the framework/library default doesn't already close it.** Many stacks auto-escape template output, sign/verify session cookies, enforce CSRF tokens by default, guard mass assignment with `$fillable`/`$guarded`/`strong_parameters`, and reject `.php` uploads. Confirm the specific defense is absent *in this code path* — a custom sink built beside the safe API, a model with no guard list, an upload dir that executes PHP — before reporting. Cite the version if the default depends on it.
5. **If confirming needs the deployed config, say so.** Whether an upload dir executes PHP, whether `phar` deserialization is reachable, whether a class with the gadget is autoloaded, and whether the web server serves a given path are sometimes deployment facts. If you cannot confirm from source, mark it "requires deployment testing" and do NOT report it as confirmed — an unconfirmable HIGH is still a false positive.
6. **Return ONLY confirmed findings** with the specific sink, the tainted path to it, and the impact — or "No exploitable server-side framework issues found" if that's honest.
